链式代理

链式代理是 MJJ 圈最常见的进阶玩法之一。它不只是“多套一层代理”这么简单，更常见的目标其实是线路优化、落地保护、分区解锁和故障隔离。把角色分清楚，再决定是否值得多加一跳，通常比盲目上链更重要。

什么是链式代理

链式代理（Proxy Chaining），也称为代理链或多跳代理，是指将多个代理服务器串联起来，让网络流量依次经过每个代理节点，最终到达目标服务器的技术。

客户端 → 代理A → 代理B → 代理C → 目标网站
         (入口)   (中转)   (出口)

MJJ 圈里为什么总在聊“上链”

  • 线路不直，直连落地机速度烂，就想用更好的中转线路把前半段补起来
  • 落地 IP 很珍贵，比如原生流媒体 IP，不想让它直接暴露在探测面前
  • 不同地区的出口各有用途，希望把解锁、延迟和成本拆开做组合
  • 有时只是“看起来高级”，但实际上使用需求并不值得增加复杂度

工作原理

数据流转过程

  1. 客户端发起请求 - 数据首先发送到第一个代理节点
  2. 逐级转发 - 每个代理节点将数据转发给下一个节点
  3. 到达目标 - 最后一个代理节点（出口节点）将请求发送到目标服务器
  4. 响应返回 - 响应数据沿原路径逆向返回客户端

加密层叠

在链式代理中，每一跳都可以有独立的加密层：

原始数据
  ↓ 加密（代理C 密钥）
  ↓ 加密（代理B 密钥）
  ↓ 加密（代理A 密钥）
最终传输数据

每个代理只能解密自己那一层，无法看到完整数据

链路角色速记

角色 职责 常见关注点
入口 客户端最先接入的第一跳 握手是否稳定、是否容易被 QoS、是否方便替换
前置 挡在核心节点前面，承接流量并转发 便宜、好换、能做分发，不一定必须很强
中转 负责改变路径，把流量送上更优线路 去程回程质量、丢包、晚高峰表现
落地 最终访问目标网站的出口 IP 纯净度、地区属性、解锁能力、封禁风险

判断一条链有没有价值，核心不是“有几跳”，而是每一跳是否明确承担了角色。如果只是把两台普通机房机器硬串起来，往往只会多延迟、多故障点，收益很有限。

常见架构模式

1. 中转加速架构

架构图

客户端 → 国内中转机 → 境外落地机 → 目标网站
        (优化线路)    (原生IP)

适用场景

  • 落地机直连速度慢，需要优质线路中转
  • 使用 CN2 GIA、IPLC 等优质线路加速

优势

  • 显著提升连接速度和稳定性
  • 降低延迟和丢包率

2. IP 保护架构

架构图

客户端 → 前置代理 → 核心代理 → 目标网站
        (可更换)    (珍贵IP)

适用场景

  • 核心代理拥有珍贵的原生 IP（如 Netflix 解锁）
  • 需要保护核心代理不被直接暴露

优势

  • 前置代理被封可快速更换
  • 核心代理 IP 得到保护

3. 匿名增强架构

架构图

客户端 → 代理A → 代理B → 代理C → 目标网站
        (地区1)  (地区2)  (地区3)

适用场景

  • 需要更高级别的匿名性
  • 防止单点追踪

优势

  • 每个节点只知道上下游，不知道完整链路
  • 增加追踪难度

4. 负载均衡架构

架构图

           ┌→ 落地机A ─┐
客户端 → 中转机 → 落地机B → 目标网站
           └→ 落地机C ─┘

适用场景

  • 多人共享，需要分散流量
  • 提高整体可用性

什么时候该上链

适合上链的情况

  • 直连落地太差 - 落地节点本身没问题，但你到它的路径很绕、晚高峰拥堵明显
  • 落地 IP 值钱 - 原生 IP、家宽 IP 或特殊地区出口不想直接暴露
  • 需要拆角色 - 想把接入稳定性、线路质量、地区解锁分别交给不同节点处理
  • 多人共享 - 想让入口统一，后面分发到不同落地做冗余

不适合上链的情况

  • 只是普通网页和日常视频 - 单节点已经稳定，继续上链只会增加复杂度
  • 对延迟极敏感 - 游戏、实时语音、远程桌面通常不适合额外多跳
  • 预算有限 - 多一跳就多一台机器、多一层排障成本
  • 不会排障 - 链路越长，越难判断是入口炸了、前置炸了还是落地炸了

一个简单判断法

如果你说不清楚“我到底是在补线路、护落地，还是做负载均衡”，通常说明还不该上链。先把单节点跑顺，再决定是否值得增加角色分工。

配置方法

Clash 配置示例

使用 relay 类型实现链式代理

proxies:
  # 定义各个代理节点
  - name: "中转节点-HK"
    type: vmess
    server: hk-relay.example.com
    port: 443
    uuid: your-uuid-here
    alterId: 0
    cipher: auto
    tls: true

  - name: "落地节点-US"
    type: vmess
    server: us-landing.example.com
    port: 443
    uuid: your-uuid-here
    alterId: 0
    cipher: auto
    tls: true

proxy-groups:
  # 链式代理组
  - name: "链式代理"
    type: relay
    proxies:
      - "中转节点-HK"
      - "落地节点-US"

rules:
  - MATCH,链式代理

说明：relay 类型会按顺序将流量依次转发经过列表中的每个代理。

Xray 配置示例

使用 outbounds 链实现

{
  "outbounds": [
    {
      "tag": "proxy-chain",
      "protocol": "vmess",
      "settings": {
        "vnext": [{
          "address": "中转服务器地址",
          "port": 443,
          "users": [{"id": "uuid-1"}]
        }]
      },
      "streamSettings": {
        "network": "tcp"
      },
      "proxySettings": {
        "tag": "landing-proxy"
      }
    },
    {
      "tag": "landing-proxy",
      "protocol": "vmess",
      "settings": {
        "vnext": [{
          "address": "落地服务器地址",
          "port": 443,
          "users": [{"id": "uuid-2"}]
        }]
      }
    }
  ]
}

说明：通过 proxySettings.tag 指定下一跳代理。

Surge / Shadowrocket 配置

[Proxy]
中转节点 = vmess, hk-relay.example.com, 443, ...
落地节点 = vmess, us-landing.example.com, 443, ...

[Proxy Group]
链式代理 = relay, 中转节点, 落地节点

优缺点分析

优点

优点 说明
线路优化 通过优质中转线路提升整体速度
IP 保护 隐藏核心节点，延长 IP 使用寿命
匿名性增强 多跳增加追踪难度
灵活性高 可根据需求灵活组合不同节点
故障隔离 单点故障可快速切换替代节点

缺点

缺点 说明
延迟增加 每增加一跳，延迟累加
速度下降 受限于链路中最慢的节点（木桶效应）
成本增加 需要维护多个服务器
配置复杂 需要正确配置多个节点的连接关系
故障点增多 任一节点故障都会导致整条链路不可用

使用场景

推荐使用链式代理的场景

  • 线路优化 - 落地机直连速度差，需要 CN2/IPLC 中转
  • IP 保护 - 拥有珍贵的流媒体解锁 IP，需要保护
  • 多人共享 - 需要负载均衡分散流量
  • 高匿名需求 - 需要更高级别的隐私保护

不推荐使用的场景

  • 低延迟需求 - 游戏等对延迟敏感的应用
  • 简单浏览 - 普通网页浏览，单节点足够
  • 预算有限 - 无法承担多服务器成本

常见误区

  • 误区 1：跳数越多越安全 - 自建链里每一跳都可能留下日志，跳数增加不自动等于匿名性提升
  • 误区 2：加前置就一定更快 - 前置只有在线路更优时才有价值，差线路前置只是在额外绕路
  • 误区 3：上链后落地就绝对安全 - 如果入口、前置和面板配置混乱，核心信息仍可能通过日志或探测暴露
  • 误区 4：链路复杂才算进阶 - 能稳定跑一台高质量落地，往往比维护三台普通机器更实用

注意事项

配置注意

  • 协议兼容性 - 确保链路中各节点协议相互兼容
  • 端口开放 - 中转节点需要能访问落地节点的端口
  • 时间同步 - 各节点服务器时间需要同步（VMess 要求）
  • MTU 设置 - 多层封装可能需要调整 MTU 避免分片

性能优化

  • 减少跳数 - 非必要不增加跳数，2-3 跳通常足够
  • 选择近距离节点 - 相邻节点地理位置尽量接近
  • 使用 MUX - 启用多路复用减少握手开销
  • 监控链路 - 定期检测各节点状态和延迟

与 Tor 的对比

特性 链式代理 Tor 网络
节点控制 自己控制所有节点 志愿者运营的公共节点
速度 较快（取决于节点质量） 较慢
匿名性 中等（节点可能记录日志） 高（洋葱路由设计）
成本 需要付费购买服务器 免费
可定制性 高 低
