SSH 与主机安全

代理服务本身只是主机上的一个网络服务。安全事故通常来自管理面板、SSH、数据库、日志或备份泄露，而不是协议名称本身。先减少暴露面，再谈协议参数。

SSH 密钥与变更流程

  1. 在本地生成并保存密钥，将公钥安装到服务器。
  2. 用新终端验证密钥登录成功后，再考虑禁用密码登录。
  3. 修改配置前保留旧 SSH 会话，准备服务商 Console 或救援模式。
sshd -T | grep -E 'passwordauthentication|permitrootlogin|pubkeyauthentication'
sshd -t
systemctl reload ssh

修改 SSH 端口只能减少扫描噪声，不能替代密钥、来源限制和 Fail2ban。

防火墙与最小暴露面

启用 UFW 前，先放行当前 SSH 端口。代理端口按实际协议放行，不要默认同时开放 TCP 和 UDP。

ufw allow 22/tcp
ufw default deny incoming
ufw default allow outgoing
ufw enable
ufw status verbose

限制管理端口来源：

ufw allow from 可信管理IP to any port 面板端口 proto tcp
公网端口原则
SSH仅开放实际管理端口，优先限制可信来源
代理端口只开放实际使用的 TCP 或 UDP 类型
80/443仅在网站、标准 TLS 或 ACME 需要时开放
数据库、面板、监控优先监听 127.0.0.1、私网地址或 WireGuard 地址

Fail2ban 与权限

apt install -y fail2ban
systemctl enable --now fail2ban
fail2ban-client status

通过 /etc/fail2ban/jail.d/ 添加本地覆盖，不直接修改软件包默认文件。Fail2ban 只降低暴力尝试风险，不能替代密钥认证。

  • 管理面板使用独立账户和强密码，不使用默认路径与默认端口。
  • 管理端口优先通过来源 IP、SSH 隧道或私网访问保护。
  • 服务、数据库和监控不应无条件监听公网。

日志与隐私

排障时可以临时提高日志级别，问题解决后恢复较低级别。不要用粗略文本替换直接修改 JSON 配置，应使用结构化编辑或官方管理方式。

日志可能包含客户端 IP、目标域名、用户标识、订阅信息和错误堆栈，应设置权限、轮转并按需要清理。备份文件同样包含凭据，必须加密并限制访问。

更新与备份

  • 定期更新操作系统、代理核心、面板和依赖。
  • 升级前记录当前版本，阅读 release notes，保留可回滚副本。
  • 备份代理配置、面板数据库、TLS 证书与 ACME 账户。
  • 备份 WireGuard 密钥、防火墙规则和 systemd 覆盖配置。
  • 定期做恢复演练，证明备份确实可用。

“配置能跑”不等于“主机安全”。任何公开面板、弱 SSH 认证、无来源限制的 SOCKS5 或未加密备份，都会把协议层的安全收益抵消。

上线前检查清单

检查项完成标准
系统处于受支持版本，时间同步正常
SSH密钥登录已用新终端验证，旧会话未提前关闭
网络安全组与系统防火墙都只放行必要端口
管理面面板、数据库和监控未直接暴露公网
备份配置、数据库、证书和密钥有加密备份并做过恢复测试
日志权限、轮转和保留周期符合实际需要
